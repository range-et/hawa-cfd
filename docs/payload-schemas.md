# Payload schemas (pydantic)

Status: first migration only ([#68](https://github.com/range-et/hawa-cfd/issues/68)).
The motion payloads in `src/hawa/motion.py` are validated by pydantic models. Every
other payload is still validated by hand. Proposed follow-ups and their order are
recorded on #68; convert them one schema per PR.

## Dependency and security rules

Hawa pins `pydantic==2.13.5` (with `pydantic-core==2.46.5`). 2.13 is the last line
that supports Rhino 8's Python 3.9, and it is end of line: pydantic 2.14 needs
Python 3.10, and later fixes are not backported. Four known advisories affect
2.13.5: [GHSA-gj4f-r7mf-jjxh](https://github.com/pydantic/pydantic/security/advisories/GHSA-gj4f-r7mf-jjxh),
[GHSA-955g-x97g-8mcp](https://github.com/pydantic/pydantic/security/advisories/GHSA-955g-x97g-8mcp),
[GHSA-qpmf-fgh3-ff25](https://github.com/pydantic/pydantic/security/advisories/GHSA-qpmf-fgh3-ff25)
and [GHSA-3r8g-cqwr-jr29](https://github.com/pydantic/pydantic/security/advisories/GHSA-3r8g-cqwr-jr29).
They stay unreachable only while every model in `src/hawa` follows four rules:

1. Subclass `pydantic.BaseModel`. No pydantic dataclasses, `TypedDict`, stdlib
   dataclasses as field types, or `TypeAdapter`.
2. Set `extra="forbid"` (the shared `motion.Payload` base does). Never `"allow"`.
3. Validate Python objects with `model_validate`. Never `model_validate_json` or
   another JSON/strings mode; `dispatch_json` already parses JSON.
4. No `Fraction`, URL or DSN field types.

`tests/test_payload_schemas.py` enforces the rules on every model it finds in
`hawa`, scans the source for the forbidden APIs, and fails if the installed
pydantic is not 2.13.5. This holds without assuming inputs are trusted: shared
`.gh`, `.npz` and recording files exist. Before changing the pin, and whenever a
new pydantic or pydantic-core advisory appears, re-check it against these rules
and record the result on #68. Last re-check: 2026-11-11 (GitHub advisory database,
pydantic and pydantic-core repository advisories, OSV and PyPI): nothing beyond
the four.

Rhino runs every script venv in one shared interpreter, and the first venv to
import a module wins. Another plugin or script could therefore load a different
pydantic before Hawa does, which would void this analysis. `hawa.motion`, the only
module that imports pydantic, checks for pydantic 2.13.5 with pydantic-core 2.46.5
before using it and otherwise raises a `RuntimeError` asking the user to restart
Rhino.

pydantic evaluates annotations at runtime. On Python 3.9, `int | None` fails at
import even with `from __future__ import annotations`; use `Optional`/`Union`.
The 3.9 CI jobs catch this when the module is imported.

## Motion v0

Producer: Grasshopper's Translation, Rotation, Oscillation, Moving Body and Motion
Case components (`MotionComponents.cs`) and Python scripts. Consumers:
`plugin.check_case` (through `motion.validate_bodies`), `jobs` (through
`motion.evaluate_motion`) and `moving_boundaries`.

| Schema | Models | Snapshot |
| --- | --- | --- |
| Moving body inside the case spec's `moving_bodies` | `Body`, `Motion`, `Sphere`, `Cylinder`, `Sdf` | [moving-body.schema.json](schemas/moving-body.schema.json) |
| Motion Evaluate job request | `MotionEvaluation` | [motion-evaluation.schema.json](schemas/motion-evaluation.schema.json) |

The snapshots are JSON Schema generated by `model_json_schema()` and are the field
reference, with units in each description. A test regenerates them from the live
models and fails on any difference. After an intended model change, regenerate them:

```sh
.venv/bin/python -c "import json; from hawa.motion import Body, MotionEvaluation; [open('docs/schemas/' + n + '.schema.json', 'w').write(json.dumps(m.model_json_schema(), indent=2) + '\n') for n, m in (('moving-body', Body), ('motion-evaluation', MotionEvaluation))]"
```

Design decisions:

- **Unversioned v0.** The payloads have no schema field. Adding one would change
  case hashes and needs a C# change. Add a version only when the shape changes.
- **Validate only.** The models never replace the payload: `model_dump` output is
  not written back, so defaults are not inserted, and `case_key`, checkpoint `spec`
  comparison and job keys stay byte-identical. Tests pin the hashes of the example
  17–20 and 32 payload shapes, recorded before the migration.
- **Grasshopper keys are declared.** `kind: "Motion"` and `kind: "Body"` are
  accepted. Motion Case removes `domain_key` before the case reaches Python.
- **Numbers.** Float fields are finite `StrictFloat`. In pydantic 2.13.5 that still
  accepts integers, which matters because C# sends `0d` as the JSON integer `0`,
  but it rejects numeric strings and booleans. `StrictInt` is used where the old
  code required `type(n) is int`: SDF `shape`, `settle_cycles`, `cycles` and `axis`.
  Booleans and `3.0` are rejected there.
- **Checks that stay hand-written.** Case-level rules (one to four bodies, uniform
  BGK without curved links or refinement, at most 150,000 cells), unique body IDs,
  the SDF interior and padding checks on the sample array, the combined Mach bound,
  and the evaluation checks that depend on the session (whole cycles, ramp, step
  budget, measurement samples, body ID present in the loads).

## Error messages

pydantic's `ValidationError` text spans several lines and links to its website.
Grasshopper shows `str(exc)` verbatim, so `motion.check` reports the first problem
as one short `ValueError` with the field path, for example
`Moving body 2 geometry.sphere.radius: Input should be greater than 0` or
`Motion evaluation settle_cycles: Input should be less than or equal to 20`.
Existing `except ValueError` callers are unchanged.

Behaviour changes from the hand-written checks:

- Unknown keys in a motion, body, geometry or Motion Evaluate request are errors.
  They used to be ignored. No current producer sends one.
- A missing `id`, `pivot` or `geometry` key is a `ValueError` naming the field,
  not a `KeyError`.
- The metric, axis and body ID type of a Motion Evaluate request are checked
  before the simulation runs, instead of after the whole evaluation.
- An explicit `"body_id": null` selects the first body, like an omitted ID.
- Numeric strings and booleans in float fields are errors. The old motion and
  evaluation checks converted them with `float()` (so `"0.5"` and `true` passed),
  and the old geometry checks raised `TypeError` on strings but accepted booleans.
  No current producer sends either.

## Mutation testing

mutmut 3 mutates only code inside functions. Field declarations and constraints in
class bodies are outside its scope, so they are covered instead by one rejecting
behaviour test per declared constraint through the public entry points
(`tests/test_motion.py`, `tests/test_runtime_rejection_edges.py`) and by the schema
snapshot, which detects any change but does not prove validation behaviour.
