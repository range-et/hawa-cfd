# Contributing to Hawa

Most contributions to Hawa are made by AI coding agents working for the maintainer,
alongside human contributors. These rules apply to both. [AGENTS.md](AGENTS.md) is
the authoritative agent entry point; this file summarises the rules and links to
the documents that define them. Where they differ, follow AGENTS.md and the linked
documents.

By contributing you agree to follow the [code of conduct](CODE_OF_CONDUCT.md).
Report security problems privately as described in [SECURITY.md](SECURITY.md).

## Before you start

- Read [AGENTS.md](AGENTS.md), [features.md](features.md),
  [docs/quality-gates.md](docs/quality-gates.md) and the relevant
  [GitHub issues](https://github.com/range-et/hawa-cfd/issues).
- GitHub Issues is the only backlog. There is no Markdown backlog. Search open and
  closed issues before filing. New issues need evidence or a reproduction, scope,
  execution surface, owner (or unassigned), next action and completion criteria.
  See [the issue workflow](docs/github-issues.md).
- Work from the latest `main` on your own branch, with one issue per branch and one
  owner per branch. Coordinate before two branches edit the same files. Shared
  generated files (the function matrix) are regenerated by whichever branch merges
  second, never hand-merged.

## Code requirements

- Python production code stays compatible with Python 3.9 and the pinned PyTorch
  dependencies, because Rhino 8 embeds CPython 3.9. MPS is PyTorch's Apple
  backend; MLX is not a backend here.
- Use two environments. `.venv` is Python 3.9 (`uv sync --extra test`): production
  parity, and the environment for every gate, script and documented command.
  `.venv-dev` is Python 3.12 (`UV_PROJECT_ENVIRONMENT=.venv-dev uv sync --python
  3.12 --extra test --group tools`) and holds developer tools that need newer
  Python: ruff and the mutmut 3.7.0 mutation studies. Nothing in `.venv-dev` is a production
  dependency, and a 3.12 pass is not evidence for 3.9.
- Rhino installs dependencies from the `# requirements:` headers in
  `plugin/Bootstrap.py` and `scripts/grasshopper_component.py`. Change those
  headers together with `pyproject.toml` (a test checks they match), then run
  `uv lock` and `scripts/export_rhino_requirements.sh`.
- Original Hawa code is GPL-3.0-only. Preserve bundled upstream license notices
  and record vendored changes in the vendor's `PORTING.md`.
- Make the smallest change that delivers the issue. Keep heavy work off the
  Grasshopper solution thread, use cooperative pause and cancel, and never block
  the UI thread.
- Preserve user geometry, documents, example 09 and archive compatibility.

## Testing requirements

Every pull request that changes code needs all of the following, in the PR,
before review.

1. **Meaningful tests** for every new or changed first-party Python or C#
   function, method, property, local function or callback. Cover the intended
   result and the relevant invalid-input and failure behaviour. Imports and
   construction-only smoke checks do not count.
2. **100% line and function coverage** of first-party headless code. Run the
   [function coverage gate](docs/function-testing.md) against the PR base, run
   `check --strict --coverage-scope headless`, and commit the regenerated matrix.
   Don't add coverage exclusions or weaken assertions to pass.
3. **Targeted mutation testing.** Run mutmut 3.7.0 from `.venv-dev` only on the
   lines the PR changes (a runner's `changed_lines` patch against the base), with
   the focused tests that exercise them; see
   [Mutation checks](docs/function-testing.md#mutation-checks). Kill
   non-equivalent survivors with new tests. Record equivalent survivors and `no
   tests` mutants with their diff hash and reasoning in a committed, reviewed
   policy. Timeouts, errors and other outcomes fail the check; they never count
   as kills. Commit the study script and policy; the CI workflow runs the CLI
   and runtime admission studies. Whole-module mutation runs are not required.
4. **The full suite passes on Python 3.9 and 3.12.** Run it with
   `.venv/bin/python -m pytest tests -q` and `.venv-dev/bin/python -m pytest tests -q`,
   and run `.venv-dev/bin/ruff check .`, which rejects syntax that Python 3.9
   cannot parse. CI runs all three. Tests that run a production entry point which
   refuses non-3.9 interpreters carry `@pytest.mark.production_python` and are
   skipped on 3.12 only. Shared-state changes also run
   `dotnet run --project tests/dotnet/StateContracts`.
5. **Device smoke gate, CPU mode.** PRs that touch numerics pass the CPU mode of
   the device smoke gate ([#57](https://github.com/range-et/hawa-cfd/issues/57))
   in CI.
6. **Local Rhino acceptance.** For code changes, the PR creator supplies the
   [local Rhino acceptance](docs/local-rhino-acceptance.md) evidence, or states why
   it does not apply. A skipped check is not a pass.

Report what you actually ran: commands, results, device, skips and omissions.
Historical results are not fresh passes.

**After merge (device qualification).** CUDA and MPS checks, including the CUDA
and MPS modes of the smoke gate, run in the next batched device round on the
merged `main` commit. Reviewers don't hold a PR for them. Their results decide
whether the linked issue closes, is re-scoped, or gets a fix-up PR.

## Numerical and device rules

- Never widen a tolerance or change a criterion after seeing results. Declare
  each comparison before running, as `bitwise`, `bounded` or `statistical`.
- Develop on CPU with a CPU FP64 reference. Compare every device against that
  reference, not CUDA against MPS. Where possible, build a CPU proxy of the
  device's precision path to debug without the device.
- CUDA and MPS checks run once per merged commit, in batched device rounds
  tracked in one issue per device. Each run posts a machine-generated manifest
  with raw results. The full protocol is in
  [the issue workflow](docs/github-issues.md#device-qualification-protocol).
- A rendered field or a finite result is not a convergence or accuracy result.
  Solver output is experimental; read the release notes and limits before
  reporting forces or coefficients.

## Pull requests and closing issues

- Use the [pull request template](.github/PULL_REQUEST_TEMPLATE.md). Use
  `Refs #N` for partial work and `Closes #N` only when the full declared scope is
  met.
- An issue that cannot meet every criterion this round may be closed after a
  maintainer-approved re-scope: list each item as passed, failed or
  unsupported-guarded with evidence, move failed items to one linked follow-up,
  and claim only passed items in `features.md`. See
  [re-scope and close](docs/github-issues.md#re-scope-and-close).
- The maintainer owns the merge decision.

## Rules for agents

- Do the assigned work yourself and stay within the issue's scope. Report
  findings outside the scope as new issues rather than fixing them silently.
- Don't push to `main`, rewrite published history, delete remote branches, change
  repository settings or trigger releases without the maintainer's explicit
  approval.
- On contributors' machines, preserve uncommitted work and the current checkout.
  Don't change global Git, package-manager or SSH configuration. Use one-off
  options and the provided authenticated tools (for example `gh` over HTTPS on
  Windows). Watch line-ending settings (`core.autocrlf`) when hashing sources.
- Never kill or restart Rhino. Quit through Rhino's normal command if a restart
  is needed, and never replace a loaded plugin assembly.
- Never print or commit secrets.
- Keep issue comments and review records concise. Link evidence; don't paste
  transcripts or large logs.
